What Is Yurrr?

Your own password vault — running on a tiny computer in your room, locked with military-grade encryption.

The Product in 30 Seconds

Yurrr is a password manager you host yourself. Two pieces work together:

⚙
Rust Server on a Raspberry Pi

A tiny server running in your home that stores all your passwords — encrypted so even if someone steals the database file, they get unreadable garbage.

🔌
Browser Extension in Brave

A popup that lets you save, search, and auto-fill passwords on any website — like the built-in password manager, but under your full control.

The User Journey

Imagine you just signed up for a new website. Here is what happens behind the scenes:

1
You submit the signup form

Yurrr's content script detects the password field and captures your credentials.

2
A banner appears: "Save password?"

The extension holds your credentials for 30 seconds and asks if you want to store them.

3
You click "Save"

Your password travels encrypted over HTTPS to your Pi and gets locked with AES-256-GCM.

4
Next time you visit, auto-fill kicks in

The extension recognizes the login form, fetches your credentials, and fills them in instantly.

💡
Why Self-Hosted?

Commercial password managers (1Password, LastPass) store your vault on their servers. If they get hacked, millions of vaults leak at once. With Yurrr, your passwords live on a Raspberry Pi in your room. The attack surface shrinks from 'the entire internet' to 'someone physically in your house.'

The Secret Handshake

How Yurrr proves you are who you say you are — without ever storing your password in plain text.

The Nightclub Bouncer

Authentication in Yurrr works like a nightclub with a very paranoid bouncer.

1
First Visit (Setup)

You show your ID. The bouncer doesn't photocopy it — instead, he takes a unique hash (fingerprint) of your face and stores that.

2
Every Visit After (Login)

You show your face again. The bouncer takes a new hash and compares it to the stored one. Match? You're in. The bouncer gives you a wristband (JWT token) valid for 1 hour.

3
Inside (Every Request)

You flash your wristband at each door. If 15 minutes pass without activity, the wristband self-destructs and you need to re-authenticate.

Password Hashing: The One-Way Fingerprint

Here is the actual code that takes your master password and creates an irreversible fingerprint using Argon2id:

CODE — crypto.rs 
pub fn hash_master_password(password: &str) -> Result<String> {
    let salt = SaltString::generate(&mut OsRng);
    let argon2 = Argon2::new(
        Algorithm::Argon2id,
        Version::V0x13,
        Params::new(16384, 2, 2, Some(32))
            .expect("valid argon2 params"),
    );
    let hash = argon2.hash_password(password.as_bytes(), &salt)?;
    Ok(hash.to_string())
}
PLAIN ENGLISH

This function takes your password and returns an irreversible fingerprint.

First, generate random "salt" — extra random bytes mixed in so two people with the same password get different hashes.

Set up Argon2id with specific difficulty settings: use 16 MB of RAM, run 2 passes, use 2 CPU threads, and output 32 bytes.

These numbers are tuned for a Raspberry Pi — hard enough to stop attackers, fast enough to not annoy you.

Run the algorithm: password + salt goes in, one-way hash comes out.

Return the hash as a string (includes the salt and parameters, so we can verify later).

03

The Vault

How your passwords are locked away with the same encryption used by intelligence agencies.

The Sealed Envelope

Imagine you write a secret message, seal it in an envelope, and stamp it with a unique wax seal. The envelope can only be opened with your specific signet ring. If anyone tampers with it, the seal breaks and the message self-destructs.

That is AES-256-GCM — the same encryption standard used by banks and governments.

Locking a Password

Here is the encrypt function. Every time you save a password, this runs:

CODE — crypto.rs 
pub fn encrypt(plaintext: &str, key: &[u8; 32]) -> Result<String> {
    let cipher = Aes256Gcm::new_from_slice(key)?;
    let mut nonce_bytes = [0u8; 12];
    OsRng.fill_bytes(&mut nonce_bytes);
    let nonce = Nonce::from_slice(&nonce_bytes);

    let ciphertext = cipher
        .encrypt(nonce, plaintext.as_bytes())?;

    let mut combined = Vec::with_capacity(12 + ciphertext.len());
    combined.extend_from_slice(&nonce_bytes);
    combined.extend_from_slice(&ciphertext);
    Ok(B64.encode(combined))
}
PLAIN ENGLISH

Takes your password (plain text) and the 32-byte encryption key.

Creates an AES-256-GCM cipher from the key — think of it as configuring the lock.

Generates 12 random bytes called a nonce. This ensures that encrypting the same password twice gives different results.

Encrypts the password. The output includes a 16-byte tamper-detection tag.

Glues the nonce + encrypted data together into one blob.

Encodes the blob as Base64 text so it can be stored in the database.

What Gets Stored

Here is what a single entry looks like in the SQLite database:

🔓

Stored in Plain Text

website_url, website_domain, username, created_at — needed for searching and listing.

🔒

Encrypted

password_encrypted, notes_encrypted — stored as Base64 blobs, completely unreadable without the key.

📚
Why Not Encrypt Everything?

If the domain and username were encrypted, you couldn't search for "github" in your password list without decrypting every single entry first. It's a tradeoff: searchability vs. secrecy. The truly sensitive data (passwords and notes) is encrypted, while metadata needed for lookup stays readable.

The Messenger

How the browser extension's parts talk to each other — and why they can't just call functions directly.

The Post Office

A browser extension has three isolated worlds that can't directly share memory:

🖼
Popup

Lives in its own little window. Opens and closes when you click the extension icon. Has its own DOM.

⚡
Service Worker

Runs in the background, even when the popup is closed. The only piece with persistent network access. Think of it as the always-on service worker.

🔎
Content Script

Injected into every web page. Can see and modify the page's DOM, but can't talk to the server directly.

The Message Hub

The service worker acts as a telephone switchboard. Every request goes through it:

CODE — service-worker.js 
chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  handleMessage(message, sender)
    .then(sendResponse)
    .catch((err) => {
      sendResponse({ error: err.message });
    });
  return true; // Keep channel open for async response
});
PLAIN ENGLISH

Set up a listener: whenever anyone (popup or content script) sends a message, this code runs.

Route the message to the handleMessage function, which is a big switch statement that picks the right action.

When done, send the result back. If something goes wrong, send the error message instead.

return true is critical — it tells Chrome "don't close the message channel yet, I'm doing something async."

Auto-Fill Magic

How Yurrr finds login forms on any website and fills in your credentials — even on tricky single-page apps.

The Undercover Agent

Content scripts are injected into every web page you visit. Their job is detective work — find login forms, even when websites disguise them.

1
Scan for password fields

Find every <input type="password"> on the page.

2
Find the matching username field

Use heuristics: check autocomplete, type="email", field names, and proximity.

3
Login or registration?

Multiple password fields = registration form. One password field = login form.

4
Act accordingly

Login? Auto-fill credentials. Registration? Show a password generator overlay.

The Fill Trick

Setting input.value = "password" seems obvious, but modern frameworks like React ignore it. Here is the workaround:

CODE — detector.js 
fillFields(usernameField, passwordField, credential) {
  const nativeSetter = Object
    .getOwnPropertyDescriptor(
      HTMLInputElement.prototype, 'value'
    ).set;

  if (usernameField && credential.username) {
    nativeSetter.call(usernameField, credential.username);
    usernameField.dispatchEvent(
      new Event('input', { bubbles: true })
    );
  }
}
PLAIN ENGLISH

Get the browser's original value setter — the one built into HTML inputs before any framework overrides it.

React and similar frameworks replace the normal .value property with their own version. If you set input.value directly, React doesn't notice the change.

Use the native setter to bypass React's wrapper. Now the DOM actually changes.

Fire an "input" event so React (and any other framework) notices: "Hey, the value changed!" The bubbles: true means the event travels up the DOM tree, reaching any parent listeners.

💡
The Native Setter Trick

This trick — using Object.getOwnPropertyDescriptor to bypass framework wrappers — is used by every major password manager and browser automation tool. It's one of the few reliable ways to programmatically fill form fields across all websites, regardless of what JavaScript framework they use.

The Credential Picker

When you have multiple accounts on one site, a dropdown appears. It's built with Shadow DOM for a good reason:

❌

Without Shadow DOM

The website's CSS bleeds into your picker. Fonts change, colors clash, layout breaks. Every site looks different.

✅

With Shadow DOM

Complete style isolation. The picker looks identical on every website — clean dark theme with green accents.

Watching for New Forms

Modern websites load content dynamically. A login form might appear seconds after the page loads. The detector handles this with a MutationObserver:

CODE — detector.js 
const observer = new MutationObserver(() => {
  if (this.scanQueued) return;
  this.scanQueued = true;
  requestAnimationFrame(() => {
    this.scanQueued = false;
    this.scanForms();
  });
});
observer.observe(document.body, {
  childList: true,
  subtree: true
});
PLAIN ENGLISH

Create a watcher that fires whenever the page's HTML changes (new elements added, removed, etc.).

Debounce: if a scan is already scheduled, don't schedule another. This prevents scanning 100 times per second when a page loads many elements at once.

requestAnimationFrame waits for the browser's next paint cycle before scanning. This keeps the page smooth.

Watch the entire page (subtree: true) for any child elements being added or removed.

Security Layers

Yurrr's security isn't one big lock — it's layers, like an onion. An attacker would need to peel through all of them:

🔐

Transport: HTTPS/TLS

All data travels encrypted between your laptop and the Pi. Even on your own WiFi, nobody can snoop.

🛡

Auth: Argon2id + JWT

Memory-hard hashing makes brute-force absurdly expensive. Short-lived tokens limit damage from leaks.

🔒

Encryption: AES-256-GCM

Each password is individually encrypted with a random nonce. Tamper-proof thanks to the authentication tag.

😵

Memory: Zeroizing Keys

Encryption keys are wrapped in Zeroizing — when the session ends, the memory is overwritten with zeros. No leftover keys in RAM.

🕓

Timeouts

JWT expires after 1 hour. Session locks after 15 minutes of inactivity. Walk away, and the vault locks itself.

📋

Audit Log

Every login, entry access, and modification is logged. If something suspicious happens, you can trace it.

Why Transactions Matter

The server uses a database transaction for the password change. If the server crashes after re-encrypting half the entries, the transaction rolls back — all entries stay encrypted with the OLD key. Without a transaction, you'd have half old-key, half new-key entries, and a corrupted vault.

What You've Learned

You now understand the inner workings of a production password manager. Here are the big ideas you can apply everywhere:

Separation of Concerns

Each component has one job. Popup handles UI, Service Worker routes messages, Server manages crypto. When things break, you know where to look.

Defense in Depth

Multiple security layers (TLS, Argon2id, AES-256-GCM, RAM-only keys, timeouts). No single failure compromises everything.

Message Passing

Isolated components communicate through structured messages. This pattern appears in browser extensions, microservices, mobile apps, and distributed systems.

Tradeoffs Are Everywhere

RAM-only keys vs. persistent sessions. Encrypted notes vs. searchable notes. Every architectural decision has a cost and a benefit.
